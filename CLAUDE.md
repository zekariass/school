Guidance for AI agents and developers working in this repository.

## Source of truth

- Product spec: `docs/Education_Platform.md`
- Resolved inconsistencies and confirmed decisions (D1–D40): `docs/Spec_Review.md`. Where they conflict, these override the spec.
- Schema: `docs/Database_Design.md`. Migrations must match it; update the doc in the same change if the schema must differ.
- Delivery order: `docs/Implementation_Plan.md`. Part A is the implementer's guide (workflow, migration numbering, definition of done, as-built template), part B the status of every milestone, part C the updates needed in built code. Work milestone by milestone, keep the definition of done, and update the status, the as-built note and part C in the same PR.

- `apps/web` is Next.js 16: read `apps/web/AGENTS.md` and the bundled docs in `node_modules/next/dist/docs/` before writing web code.

## Monorepo conventions

- Shared packages live in `packages/*` as **source-only TypeScript** (`exports` point at `src/*.ts`, no build step). Next.js (Turbopack) and Expo (Metro) compile them directly. Keep them framework-agnostic: no React Native or Next.js imports.
- Generated files are committed: `packages/api-client/src/generated/`, `packages/design-tokens/generated/`. Never edit them by hand. Regenerate with `npm run codegen`; CI runs `codegen:check`.
- New packages extend `@school/config/tsconfig/library.json`, re-export `@school/config/eslint/library`, and provide `lint`, `typecheck` and `test` (vitest) scripts.
- Node version: `.nvmrc` (26). The design-token script relies on Node's built-in TypeScript type stripping.

## Web conventions (`apps/web`, Next.js 16)

- Every page lives under `app/[locale]/`. Use next-intl's `Link`/`useRouter` from `@/i18n/navigation`, never `next/link` for internal routes. All text comes from `useTranslations` / `getTranslations`.
- `cacheComponents` is on: never read `cookies()`, `headers()`, `params` or `searchParams` at the top of a layout. Read them inside a `<Suspense>` child. `npm run build -w school-web` fails on violations.
- The browser calls the API only through the BFF (`/api/bff/api/v1/...`, via `lib/api-client.ts`). Server Components and Server Actions use `createServerApi()` from `lib/server/api.ts`. Tokens live in httpOnly cookies (`lib/server/session.ts`) and never reach client JavaScript.
- `proxy.ts` auth checks are optimistic only (it also renews the access token silently, see `lib/server/session-core.ts` and `refresh.ts`). Server Components get the user from `requireSession()` (`lib/server/dal.ts`, `GET /me`), inside `<Suspense>`; every Server Action re-validates its input and relies on the API for authorization.
- Mutating Route Handlers under `/api/auth/*` and `/api/bff/*` call `guardOrigin()` (`lib/server/responses.ts`, rules in `lib/origin.ts`). Tokens are set only by Route Handlers and the proxy, never returned to the browser.
- Console data comes from TanStack Query through the BFF; creates use `useSubmit` (`components/console/use-submit.ts`), which sends an `Idempotency-Key`. Show the API's localized `problem.detail` for failures.
- Images come from `<MediaImage mediaId variant>` (signed URL from `GET /media/{id}/url`, cached ~4 min; plain `<img>`, not `next/image`); uploads go through `lib/media/upload.ts` and `<ImageUploader>` (limits come from `GET /media/policies`).
- UI primitives are shadcn/ui in `components/ui`, styled by `@school/design-tokens`. Don't add per-component colors.

- Guardians and invitations: public pages (`/invite/{token}`, `/connect`) live in the `(invite)` group, with their secret only in the URL path (token) or in component state (printed code), never in storage, query keys or logs. Their Route Handlers (`/api/invitations/*`) attach no session, whitelist input (`lib/server/invitation-input.ts`) and only `accept` sets cookies. The BFF refuses token-issuing endpoints (`isTokenIssuingPath` in `lib/bff.ts`): a new endpoint that returns tokens needs its own Route Handler and an entry there. Parent codes follow the login-code rules (`IssuedCodesProvider.putParent`, no `Idempotency-Key`). Guardian-screen logic shared with mobile lives in `@school/validation/{guardians,family}`; custody-restricted links must never render for non-administrators (the API withholds them, the panel filters again).
- Calendar (`app/[locale]/(app)/calendar`, `/s/[school]/calendar`, `components/calendar`, `lib/calendar`): pure logic in `lib/calendar` (grids, windows, bucketing, recurrence, occurrence ids, RSVP, form payloads; the display calendar and Ethiopian months via `@school/calendar`, never edited from here). Items go on days **in their own time zone** (all-day by `startDate`/`endDate`, never `endAt`; timed by instants) and are shown in it; the browser's zone is only for "today" and the "your time" note; every form shows and sends an explicit zone. Always send `sources` explicitly. Event text (titles, places, descriptions, meeting participants) lives only in TanStack memory with `gcTime` `CALENDAR_GC_MS`: never in URLs (ids only), storage (only the `school.calendar` display choice), logs or the document title. Show only what the API sent (totals, `participants`, `capabilities`): do not derive or filter. Keep `family.*` messages plural-free (shared with the phone).
- School workspace (`app/[locale]/(app)/s/[school]`, `components/school`, `lib/school`): visibility of menu items and buttons is derived from `/me` by pure functions in `lib/school/access.ts` and `class-view.ts` (the API stays the authority; handle its 403/404/409 problems inline). Teachers have no `school.read`, so `getWorkspaceSchool()` (DAL) resolves their school from `memberships`. Login-code plaintext exists only in `IssuedCodesProvider` memory and in the QR (`qrPayload` = the bare token): never put codes in URLs, storage, TanStack Query data or logs, and never send an `Idempotency-Key` on the issue call.

- Points screens (`components/points`, `lib/points`): every award is one `clientOpId` per user action, kept by `createOpTracker` while the same action is retried and renewed after a success (never regenerate it on retry; never send `Idempotency-Key` on awards). The class overview is eventually consistent: update it from the award response (`applyDelta`) and refresh through `overviewRefresher` (debounced per class), never right after each call. Undo countdowns live in `PointsProvider` memory only (single award: reverse the row, several: the batch). The only browser storage is the mute preference; no child data or notes in URLs, storage or logs. Skills and badges store icon *names* (`lib/points/icons.ts`), not emoji. School points and home points are separate sections and are never summed. Sound is WebAudio-synthesized (no assets) and motion must respect `prefers-reduced-motion`.

- Attendance screens (`components/attendance`, `lib/attendance`): attendance dates are the school's, taken from the roll/dashboard response's `timeZone` (`localDateIn`), never the browser's. A roll write carries each record's `expectedVersion` and the roll's `baseVersion` from the roll the edits were made against (`base` in `class-attendance-tab.tsx`, which must not follow background refetches while edits are unsaved); `PUT .../attendance` answers 409 *with a result body* for conflicts, so use `putRoll`, not `unwrap`. Roll marks, teacher notes and absence-report reasons/notes stay in component memory and the TanStack cache only (never storage, URLs or logs). Per-period rolls (M7d): slots come from the API's `slots`; the roll on screen carries its `subjectId` (fixed once the roll exists) and `groupId` into every write, and each slot/group has its own query key. Staff attendance (`staff-tab.tsx`, `lib/attendance/staff.ts`): the tab exists only for `school.staff_attendance.read|manage` and there is no teacher-facing staff view; staff names, notes and correction reasons follow the same memory-only rule (short `gcTime`); the setting `attendance.staff.enabled` is learned from the API's 403 `staff_attendance.disabled`, never assumed. Component tests render with `react-dom/server` and a seeded query cache (`*.test.tsx`).
- **Feed (`components/feed`, `lib/feed`):** posts, stories, contributions and comments are shown exactly as the API answers (`rights`, `mediaWithheld`, missing `author.displayName`, optional `seenCount`); never filter or guess on the client. Consent-gate failures (422 `feed.media_consent_missing` / `feed.media_confirmation_required`) are parsed by `lib/feed/consent-error.ts` and shown with `<GateNotice>`; the composer never loses the author's text or photos. Scheduled times are picked and shown in `capabilities.timeZone` (`lib/feed/schedule.ts`), never the browser's zone. Feed query data lives under `fk` keys in memory only; post text, captions, student names and signed URLs never go into URLs, storage, logs or analytics (ids only in paths). The tabs Feed | Photos | Activities | Achievements are server-side filters (`type`, `photos` via `lib/feed/tabs.ts`, one query key per tab): never filter or group posts on the client. Feed notification links resolve in `lib/notifications/deep-link.ts` (`/feed/posts/{id}` and `/feed/stories/{id}` need the notification's `schoolId`, `/feed/approvals` the school slug from `/me`).

- Announcements (`components/announcements`, `lib/announcements`): titles and bodies are plain text, rendered only through `PlainText` (React escaping + `linkify`, http/https links only) and never put in URLs, storage or logs; controls follow `GET .../announcements/capabilities` and each announcement's `can.*`; publishing is create-as-draft, count (`/preview`), confirm, then `/publish` or `/schedule`; scheduled times are picked in the school's time zone from the capabilities; after a published edit `material` must be chosen by the author; show the API's `problem.detail` and, for 429, `ApiRequestError.retryAfter`.

- **Messaging UI (`components/messaging`, `lib/messaging`):** the screens run at `/messages/**` and inside the workspace at `/s/{slug}/messages/**` (`MessagesPlaceProvider` carries the base path and the viewer). Show or hide controls only from the API's `capabilities`, `canPost`, `myRole`, `canModerate`, `canEdit`/`canDelete` and `guardiansCanSee`; never add policy logic. Message text, names, drafts and recipients stay in memory (short `gcTime`, messages removed on leaving a conversation): never in URLs (ids only), storage, titles, toasts or logs. Render text only through `messageSegments` (plain text, strict http(s) links). Reuse the same `clientMessageId` when retrying the same message (`lib/messaging/composer.ts`). Live updates are doorbells (ids only) from `/user/queue/messages` that refetch through the API, with polling when the socket is down. A student has no directory: never build a people picker for students. The review UI (`review-view.tsx`) is reviewer-only and every read needs the typed reason.
- **Moderation, safeguarding and student sign-in (`components/moderation`, `components/safeguarding`, `lib/moderation`, `components/auth`, `lib/auth`):** reporting goes through the one `ReportDialog` (`POST /moderation/reports`, an `Idempotency-Key` per dialog, ids and the reason code plus optional details of at most 1,000 characters; the answer is only the generic thank-you, never a case or an outcome; emergency text comes from `GET /safety/emergency-info` for the page's own country, never written in the app); a new reportable target is one entry in `REPORTABLE_TARGETS` once its API bean exists (portfolio items and announcements have none yet). Queue and case controls come from `caseControls` (`lib/moderation/access.ts`: the case's status, queue and history plus the viewer's permissions), the API decides again and its 403/409 are shown inline. **A 404 is "nothing here"** (`NothingHere`, the words of an unknown page): incidents answer 404 to everybody but leads, so a person without `school.safeguarding.read` gets that page and no request is made, a 404 replaces the whole page, and no text says what the page is for or that it exists; the menu shows safeguarding to leads only. Reporter identity and report details appear only when the API sent them (`reporterIdentityVisible`, `reporterId`, `details`): never guess or fill them in. What is read per view (a case's detail, the reported content, an incident's narrative and notes) has `gcTime` 0, content and incidents are read only when the person asks (every read is audited and rate limited), incident text lives in component state, every moderation mutation has `gcTime` 0, and nothing of it goes into a URL (ids only; `generateMetadata()` takes no parameters), storage, a toast or a log (`components/moderation/privacy.test.ts` scans for it). Text is shown as text: no links, no markup. The student sign-in (`/student-code`, D41): the page scans the QR code with `getUserMedia` (asked only on a button press; jsQR is loaded by a dynamic import only there; `Permissions-Policy` allows the camera on that one page in `next.config.ts`) or takes the typed code; the code stays in component state (never a URL, storage, query key or log) and goes once to `POST /api/auth/login-code`, which calls `guardOrigin()`, forwards exactly `{ code }` after `parseLoginCodeInput` (a bare QR token or a complete text code), attaches no session and no `Idempotency-Key`, relays the API's failure unchanged (every wrong, expired or revoked code and an inactive school is the same 400, shown as the API's sentence; a 429 shows `Retry-After`), sets the httpOnly cookies like the OTP route and returns only `{ ok: true }`. Code helpers shared with other clients live in `@school/validation/login-code`.

- **Portfolio screens (`components/portfolio`, `lib/portfolio`, rule book `docs/Portfolio_Rules.md`):** a student's own portfolio at `/portfolio`, one item at `/portfolio/items/{schoolId}/{itemId}` (and `/s/{slug}/portfolio/items/{itemId}` in the workspace), the guardian's view at `/family/portfolio[/{studentId}]` (`GET /me/portfolio`), the school gallery at `/s/{slug}/portfolio` and a "Portfolio" tab on the class page (review queue, class gallery, teacher quick capture). Show or hide controls only from what the API returns: `GET /portfolio/capabilities` (`studentMayCreate`, `canCapture`/`captureClassIds`, `reviewer`, `maxVisibility`, `itemTypes`), each item's `capabilities` (`itemActions` in `lib/portfolio/actions.ts`), `status`, `effectiveVisibility`, `mediaWithheld` and `media`; never add policy logic, never filter a list. Titles, descriptions, reflections, writing, review notes, history notes and comments live only in TanStack memory (keys under `pfk`, `PORTFOLIO_GC_MS` three minutes) and are plain text (React escaping, no links): never in URLs (ids only), storage, the document title (always the static "Portfolio"), toasts (generic sentences), logs or analytics. Signed links come from `<MediaImage>` (small renditions in lists, MEDIUM only in the viewer) and a PDF opens through a one-time original link that is never kept. Uploads use purpose PORTFOLIO with context SCHOOL (`<FileField>`, file types narrowed per item type by `allowedMimeTypes`); a create or capture keeps its `Idempotency-Key` while the same body is retried (`submissionFingerprint`), a comment uses `useSubmit`. The consent gate (422 `portfolio.media_consent_missing` / `portfolio.media_confirmation_required`) is parsed by `lib/portfolio/consent-error.ts` and shown inline with `<GateNotice>`: an author may untag a child or confirm that nobody without consent appears (the box is offered with files and no tag, and a changed file or tag drops it), a reviewer cannot confirm for the author (the approval dialog explains, offers a narrower audience and keeps the note); the form never loses what was typed or uploaded. A student's audience choices stop at `capabilities.maxVisibility`; a reviewer may only narrow (`reviewVisibilityChoices`). History is asked for only when the API sent `taggedStudents` (student and reviewers), comments only when the item says `canComment` or has comments, and authors of comments appear by the API's role label. The web builds TEXT, PHOTO, SCAN and DOCUMENT (DRAWING is the phone's canvas, AUDIO and VIDEO are refused by the API). Keep `family.portfolio.*` plural-free (shared with the phone).

- **Country, zone, calendar and languages (D42):** nothing names a country. Signed-in layouts put the display place into context (`components/display-place.tsx`: the person's place from `/me` under `(app)` and `(platform)`, the school's own zone and calendar default in the workspace, the platform default country from `GET /meta` on public pages); `useFormatInstant`, `useMessageTime` and `useCalendarPreference` read it, and the calendar offered is limited to the country's `calendarCodes` (the saved `school.calendar` choice, else `/me.calendarPreference`, else the school's or country's default; never Ethiopian where the country lacks it). Pure choosing lives in `@school/validation/country`. Phone fields take the country from `/meta` (`usePhoneCountry`; a picker only when several countries are enabled), a school's from `useSchool().school.country`; the Route Handlers forward only a `^[A-Z]{2}$` country (`lib/server/country-input.ts`). Content languages (announcements, names of skills and badges) are the school's `country.languageCodes`, named by `languageLabel` from `@school/i18n`, never a list in code.

## Mobile conventions (`apps/mobile`, Expo SDK 58)

- iOS and Android only. Routes live in `src/app/` (Expo Router); logic lives in `src/lib/`; UI primitives in `src/components/ui/` are built on `@school/design-tokens`.
- Text comes from `use-intl` (`useTranslations`) with the shared `@school/i18n` catalogs, the same keys as the web.
- The API is reached through `src/lib/api.ts`. The refresh token lives only in `expo-secure-store`; never store tokens in AsyncStorage, SQLite or the query cache.
- Photos are converted to JPEG and shrunk on the device (`lib/media/upload.ts`) before upload; show them with `<Avatar>`/`useMediaUrl` (signed links are never persisted in the query cache). Physical-device uploads need `SCHOOL_STORAGE_PUBLIC_ENDPOINT` set to the LAN address (README, Media storage).
- Guardians: the `guardian` role comes from a GUARDIAN membership or from an account that holds nothing yet (a parent whose link still waits). `invite/[token]` and `parent-code` are open to anyone; `+native-intent.ts` maps invitation web links to them (`SCHOOL_UNIVERSAL_LINK_HOST` turns on associated domains in `app.config.ts`). Children, consent and invitation previews live under the `family` query root and are never persisted (`isPersistableFamilyQuery`); the shared `family`, `invite` and `consent` message namespaces must stay plural-free (a test enforces it, like `mobile.*`).
- **Announcements** (`lib/announcements`, `app/announcements`): memory only like the feed: keys under the `announcements` root, kept out of the persisted cache by `lib/query/persistence.ts` (one tested predicate over every private root; add a new private root there). Texts are rendered as text (`LinkedText`, links only for http/https); build the composer from `capabilities` (school time zone from `capabilities.timeZone`); publish and schedule go draft, preview, confirmation sheet, then `/publish` or `/schedule`; only `createAnnouncement` carries an `Idempotency-Key`. Ask for a confirmation again from `mine.reacknowledgementNeeded`, never from `acknowledgedRevision < revision` (every edit raises the revision). Catalog keys by enum value live in `labels.ts` and a test checks that every `mobile.announcements.*` key exists in en and am.
- **Calendar (M11c)** (`lib/calendar`, `components/calendar`, `app/events`): memory only like the feed: keys under the `calendar` root, kept out of the persisted cache by `lib/query/persistence.ts`, `gcTime` five minutes; titles of parent meetings may name a child, so nothing about an event is ever stored, logged or cached on disk (no offline calendar: the screens say so), and sign-out clears the query cache. The only persisted thing is the Gregorian/Ethiopian display choice (`CALENDAR_STORAGE_KEY`). All dates are Gregorian `YYYY-MM-DD` keys (`civil.ts`); the Ethiopian calendar only decides which keys make a month and what number a cell shows (`grid.ts`, via `@school/calendar`, which this app never edits). Time zones are always explicit (`zone.ts`: only `Intl.DateTimeFormat` with `timeZone` and `formatToParts`, cached per zone): all-day items are placed by their inclusive `startDate`/`endDate` (never by `endAt`), timed items by their instants in THEIR OWN `timeZone` (`bucket.ts`), a window is the visible days padded by 14 h (`window.ts`), and forms hold wall-clock dates and minutes in the EVENT's zone (the school's from `GET /events/capabilities`, the account's for a personal event) and send explicit `timeZone` plus instants (`form.ts`); the phone's zone is only used to say that an event's zone differs. Build the form from `capabilities` and `CalendarEventView.capabilities` (`event-model.ts`); update requests carry only what changed (a schedule field clears the series' exceptions and resets answers, so the form warns first); occurrence endpoints take the `occurrenceId` of the item (`occurrence.ts`); only the two creates carry an `Idempotency-Key`. A notification path `/calendar/events/{id}` opens `/events/{id}` (`routes.ts`; the event id is global, no school lookup). Keys chosen at run time are listed in `catalog.test.ts` (every `mobile.calendar.*` key must exist in en and am, no ICU plural). `lib/calendar/fixtures/payloads.json` holds real API answers for `contract.test.ts`; record them again when the API changes shape.
- **Country, zone, calendar and languages (D42):** `PlaceProvider` (`lib/country/place.tsx`, below the session) gives the person's place from `/me`, else the platform default country from `GET /meta` (`lib/country/queries.ts`, public, no token, memory only), and replaces `usePreferences().calendar`/`calendars` (saved device choice, else `/me.calendarPreference`, else the place's default, limited to the country's `calendarCodes`; the settings and calendar screens show the toggle only with two or more). Zones come from `usePlace()`/`useDisplayZone()`/`usePlaceOfSchool(id)` or the API's `timeZone`, never a constant; phone fields use `usePhoneCountry` (picker only when several countries are enabled); a school's content languages are `usePlaceOfSchool(id).languageCodes`, named with `languageLabel` (Hermes may lack `Intl.DisplayNames`: it falls back to the native name or the code); fonts follow the language's script (`scriptOfLocale`), not its code. Pure choosing lives in `@school/validation/country`.
- Anything dev-only must be guarded by `__DEV__`, both the route (`Stack.Protected`) and its entry points.
- Keep pure logic free of React Native imports so vitest can test it (`npm run test -w school-mobile`).
- Native folders (`ios/`, `android/`) are generated by prebuild and git-ignored.
- **Feed privacy (M8c):** posts, comments, stories, tagged students' names and photo ids are children's data. They live in TanStack Query under the `feed` key (`lib/feed/keys.ts`), which `isPersistableFeedQuery` keeps out of the persisted cache, with a short `gcTime` and at most `FEED_MAX_PAGES` pages; never copy them into AsyncStorage, SQLite, a log or an offline queue (posting needs a connection; the draft lives only in the composer screen's state). Show feed photos with `<FeedImage>` (`cachePolicy="memory"`, THUMB/SMALL in lists, MEDIUM only in the photo and story viewers) and never persist a signed link. Menus and buttons come from the post's `rights` and `GET /feed/capabilities`; consent-gate 422s (`feed.media_consent_missing` with `students`, `feed.media_confirmation_required`) are explained in the composer without losing the text or photos (`lib/feed/gate.ts`). Scheduled times are picked and shown in `FeedCapabilities.timeZone`, never the phone's zone. A notification path to a post or story carries no school id: resolve it with `usePostAnywhere` / `useStoryAnywhere`. The tabs Feed/Photos/Activities/Achievements are server-side filters (`lib/feed/tabs.ts`: one query key each, never filter or group posts on the phone), tinted surfaces are the theme's primary colour at low strength (`<Tint>`, never a hard-coded or purple colour), and a child's picture shown in a feed uses `<Avatar memoryOnly>`.
- **Messaging privacy (M9c, `lib/messaging`, `components/messaging`, `app/messages`):** message bodies, drafts, names, member lists and media ids are children's data and live in memory only: queries sit under the `messaging` root (`isPersistableMessagingQuery`, wired into `lib/query/persistence.ts`, `gcTime` 3 minutes, bounded pages), the draft lives in the composer's state, and unsent messages live in the **memory-only outbox** (`lib/messaging/outbox.ts`, never SQLite/AsyncStorage: retried with the same `clientMessageId` and backoff, in order per conversation, 429 honours `Retry-After`, other 4xx are final and show the API's `problem.detail`, lost when the app closes, cleared by `clearMessagingMemory()` at sign-out and when the session ends; the conversation screen warns before leaving with unsent messages). Text is rendered only through `LinkedText` (http/https, in-app browser), never logged, never put in a route, a push or a notification title; the realtime doorbell (`/user/queue/messages`) carries ids only: fetch the message through the API. Controls come from the API's flags and `capabilities` (`canPost`, `myRole`, `canModerate`, `canEdit`, `canDelete`, `guardiansCanSee`, `timeZone`), never from client-side policy; observers and closed conversations get no composer; students get no people picker or search (guardian: a child's teachers from `/contacts`; teacher: a class, a student, then a guardian label); refusals are shown as the API's generic sentence and never explained; a scheduled time is picked in `capabilities.timeZone`. Messaging catalog keys are `mobile.messaging.*` (plural-free, checked against the code by `catalog.test.ts`).
- **Portfolio privacy (M12c, `lib/portfolio`, `components/portfolio`, `app/portfolio`):** a portfolio is children's own work, photos, notes and comments, so **none of it is stored on the phone**. Queries sit under the `portfolio` root (`isPersistablePortfolioQuery`, wired into `lib/query/persistence.ts` and tested), `gcTime` 3 minutes, bounded pages, `networkMode: 'online'`: opened offline, every screen says "needs a connection" (`listState`, `NeedsConnection`) and never shows an old copy. Drafts live in the composer's reducer only (no SQLite, AsyncStorage, file or outbox: saving needs a connection and the screen asks before closing), the converted photos are deleted when uploaded or when the screen closes, and signed links are never persisted. Titles, descriptions, reflections, review notes, comments and names are never logged, never put in a route (ids only: `schoolId`, `itemId`, `classId`, `studentId`), a push or a notification title; `lib/portfolio/privacy.test.ts` scans the portfolio sources for storage, files, `console` and non-id route params. Controls come only from the API: the item's `capabilities`, the school's `capabilities` (`studentMayCreate`, `captureClassIds`, `reviewer`, `maxVisibility`, `itemTypes`), `status`, `effectiveVisibility`, `mediaWithheld` and the comment flags; never filter or derive them from a role. Consent-gate 422s (`portfolio.media_consent_missing` with `students`, `portfolio.media_confirmation_required`) are parsed by `lib/portfolio/gate.ts` and explained inline without losing the words, pictures or tags; show the API's `problem.detail` for every other failure. Photos go through `pickPhoto`/`prepareImage`/`uploadImage` (purpose PORTFOLIO, context SCHOOL) and `usePhotoUploads`; an `Idempotency-Key` only on the creates (item, quick capture, comment), reused only for the same unchanged request, never on review, archive, feature or submit. A reviewer lowers the audience while approving, never raises it; a student's audience choices stop at `maxVisibility`. A notification path `/portfolio/items/{id}` opens `/portfolio/item/{id}` (`lib/notifications/routes.ts`). Catalog keys are `mobile.portfolio.*` (plural-free; `catalog.test.ts` checks them against the code and finds dead keys); enum labels live in `lib/portfolio/labels.ts`.
- **Reporting (M13c, `lib/moderation`, `components/moderation`):** every Report action opens the one `<ReportSheet target={{ type, id, schoolId }}>` and sends `POST /moderation/reports` (ids, a reason code, optional details of at most 1,000 characters; one `Idempotency-Key` per user action, kept for a retry of the same report); never add a per-module report call. Where the action appears follows the item's own flags (`lib/moderation/visibility.ts`: status, `rights`, `mine`, the author id the API sends), never the viewer's role and never a policy. What the person types lives only in the sheet's state (it is mounted only while a target is set): never in a route, storage, a query, a log or a notification; the only query is the safety text under the memory-only root `moderation` (`isPersistableModerationQuery`, cleared by `clearModerationMemory` at sign-out and when the session ends). A report needs a connection (no outbox). A 404 always shows the same generic "not found" (`classifyReportFailure`), other failures the API's `problem.detail` (429 with `Retry-After`). The app writes **no safety text**: the thank-you is generic and the only safety line is `GET /safety/emergency-info` for the school's country (else the person's), shown only if the API sent it. `REPORT_ACKNOWLEDGED`/`REPORT_REVIEWED` and the moderators' paths (`/moderation`, `/safeguarding`) open nothing on the phone. Catalog keys are `mobile.moderation.*` (plural-free, checked by `catalog.test.ts`).
- **Hermes has no `Intl.PluralRules`:** an ICU `plural` in a message throws FORMATTING_ERROR on a device. Keep `mobile.*` messages plural-free (a test enforces it) and never use a plural-bearing shared key (e.g. from the web catalogs) on mobile without checking.
- **Offline outbox and cache (`lib/sync`, `lib/offline`, `lib/attendance`):** teacher writes that must work offline (attendance marks `ATTENDANCE_MARK`, point awards `POINT_AWARD`) are never sent straight from a screen. They are queued in SQLite (`outbox_operations`) and sent in order, in batches, over `POST /api/v1/sync` with one `clientOperationId` per user action (= the award's `clientOpId`; no `Idempotency-Key`), until the server answered: APPLIED and DUPLICATE (of an applied operation) are done, `retryable` results, 429, 5xx, network errors and 401 keep the row and repeat the SAME operation with backoff; CONFLICT (per-student, nothing overwritten), REJECTED and an expired operation become rows with a status that the teacher must settle (`SyncEngine.attention()`: "keep theirs / use mine" sends a NEW operation with `expectedVersion`; REJECTED shows the API's `problem.detail`). `lib/sync/engine.ts` is pure (injected storage, transport, clock, owner) and tested in vitest; `runtime.ts` is the device wiring (flush on start, reconnect, foreground and a 15 s timer; taps are debounced into one request). An operation that was ever handed to the network is never edited again (the server may have applied it), so only untouched attendance edits of the same roll are merged. Rows hold ids, marks and numbers only: **no names, tokens, point notes or attendance notes** (an attendance note travels in memory only, `volatile`, and is lost if the app closes before it is sent; the mark is not). Attendance dates come from the school's time zone (`lib/attendance/dates.ts`), never the phone's. Everything is owner-scoped and wiped by `wipeOfflineData()` at sign-out and when the session ends (another user's rows are discarded unsent). The offline read cache (`offline_cache` table, `OfflineCache`) holds per class the roster (id, display name, avatar media id), the roll (ids, marks, versions, only the absence reason CODE, never notes or parents' words), the points skills, totals per student id and routine templates, with a maximum age per kind, purged for classes the teacher no longer teaches on the next successful class-list refresh, and no signed media link ever; query keys of rosters, points and attendance are excluded from TanStack's persisted cache (`isPersistable*Query`). A roll older than 3 days is shown, not edited. A teacher whose refresh token is on the phone opens the app offline from `offline-identity.ts` (name and role codes, 7 days) and the session is renewed on the first reconnect. Sounds are original synthesised WAVs from `apps/mobile/scripts/generate-sounds.mjs` (committed outputs in `assets/sounds`); the mute flag is a plain preference and the OS "reduce motion" setting turns the animation off. To check the protocol against a running API: `SYNC_E2E_FIXTURE=<json> npx vitest run src/lib/sync/e2e.test.ts` (skipped otherwise).
- Parent invitations work while the school is ONBOARDING or ACTIVE (Spec_Review D12); custody-restricted guardian links are invisible to teachers (D9).
- Student sign-in by class code only works when the school is ACTIVE; a freshly created school is ONBOARDING, and every failure looks like a wrong code. Activate the school (platform console or `PUT /platform/schools/{id}/status`) before testing student sign-in. Configure native behaviour in `app.json` and config plugins.

## Backend conventions (`apps/backend`, `com.nemaz.school`)

- **Modules:** each direct subpackage is a Spring Modulith module with `api` / `application` / `domain` / `infrastructure` subpackages. Use other modules only through their top-level package or events; `ModularityTest` enforces this. `common` is the shared kernel and `system` the technical platform.
- **Errors:** throw `ApiException` with a stable snake_case `code` (e.g. `ApiException.forbidden("class.access_denied")`) and add `error.<code>` to *both* `messages.properties` and `messages_am.properties` (`MessagesTest`). Never return stack traces or internal messages.
- **Events:** publish domain events inside the transaction. Listeners use `@ApplicationModuleListener`, are **idempotent** (delivery is at-least-once), and never call back into the publisher synchronously.
- **Recurring jobs:** `@Scheduled` + `@SchedulerLock(name = "<module>.<job>")`. A locked method returns `void` or an object (e.g. `Integer`), never a primitive: ShedLock then throws on every run, and integration tests (scheduling off) would not notice (`SchedulerLockMethodsTest`).
- **Time and ids:** inject `Clock`; use `Ids.newId()` / Hibernate `@UuidGenerator(style = VERSION_7)`.
- **Lists:** keyset pagination with `CursorPage` / `Cursors`, never offsets.
- **API changes:** run `npm run openapi:export -w school-backend`, then `npm run codegen`, and commit both the spec and the generated types.
- **Authorization:** check permissions server-side with `@PreAuthorize("@authz.school('<permission>', #schoolId)")` (also `platform`, `country`, `organization`, `campus`, `anywhere`, `anyAt`) or `AccessControl` (`common.security`); filter lists with `AccessControl.accessible(...)`. Permission codes live in `common.security.Permissions` and `R__40_roles_permissions.sql` (kept equal by a test). Actors come from `CurrentUser` (never parse ids from requests).
- **Audit and idempotency:** mutations call `AuditLog.record(...)` in their transaction (no secrets, mask phones/emails with `Masking`); create endpoints get `@Idempotent`.
- **Media (`media` module):** clients upload straight to object storage with a presigned PUT, then `complete`; never proxy bytes through the API. Access follows the owning object (R-30): the module that owns a purpose registers a `MediaPurposePolicy` bean (`canCreate`/`canRead`); `media` depends on none of them. Other modules use `MediaService` (`requireAttachable`, `summary`, `discard`) and clear their references on `MediaDeleted`. Images are served only as re-encoded variants (metadata stripped); never issue a signed URL for an image original. A new purpose needs a row in `PurposeRules` and a policy, plus allow/deny tests and matrix entries.
- **Notifications (`notifications` module):** other modules call `NotificationService.notify(NotificationRequest)` (in the caller's transaction; recipients get title and body rendered from `notification.<type>.title|body` in their language, `data.path` is a relative app path, never secrets). Notification types are data: a new type needs a row in `R__50_notification_types.sql` and `.label`/`.title`/`.body` keys in both message bundles (`NotificationTypesSeedTest`). Listeners that notify must be idempotent (`alreadyNotified`). Pushes go through the `PushSender` SPI (`school.push.provider=expo|log`).
- **Real-time (`realtime` module):** push to a user's open apps with `RealtimePublisher.toUser(...)` (Redis pub/sub across instances, best effort: anything that matters is also stored). Clients may only SUBSCRIBE to `/user/queue/*` and never SEND; CONNECT is authenticated by bearer token or a single-use ticket (`StompAuthInterceptor`). A new revocation trigger must go through `TokenService` so `SessionsRevoked` closes the sockets and push devices.
- **Classes and people (`academic`, `people` modules):** ask "may this user see/teach/manage class C" only through `academic.ClassAccess` (`canView`, `canTeach`, `canManage`, `visibleClasses` = a SQL predicate for list queries; later modules add view rules, e.g. guardians, as `ClassAccessRule` beans). Teachers and students are not role assignments: they are `school_staff`/`school_students` plus `class_teachers`/`class_students` rows. School-scoped endpoints answer 404 to callers who cannot see the school (or the class/student) and 403 to members who lack the permission (`common.security.SchoolGate`, `academic.application.ClassLookups`). `people` depends on `academic` and `identity` ports, never the reverse; to reach another module's people data add a port interface (see `SchoolPeople`, `AccountMemberships`). Student personal data (date of birth, gender, username) is shown only at `DataAccessLevel.FULL`; keep new student DTOs on the same split. Login codes (`people.LoginCodeService`) are never logged, audited or put in events; only their HMAC is stored.
- **Roster import (`imports` module):** a job is one `import_jobs` row walking UPLOADED, PREVIEWED, VALIDATING, VALIDATED, COMMITTING, COMPLETED (or FAILED/CANCELLED); dry run and commit are Modulith events (`ImportDryRunRequested`, `ImportCommitRequested`) whose listeners take the job's lease first and write the job row only in short `REQUIRES_NEW` transactions (a lock held by the listener's own transaction blocks the batches). Rows hold children's PII (`import_job_rows.raw_data`/`normalized_data`): never in logs, audit metadata or events; the retention job purges them. Other modules are written only through `people.PeopleImports` and `academic.StructureImports` (+ `ClassMemberships`), which skip permission checks because the import checked `school.import.manage`; an import never grants an administrative role and never creates a guardian (contacts go to `guardian_contact_candidates` for M5). Add a column or import type in `ImportType`, `HeaderSynonyms`, the handler, `import.field.*`/`import.row.*` messages (en + am) and the templates. Row problems are codes (`import.row.<code>`) rendered when read. `student_profiles.name_fold` (`common.text.PersonNames`) must be kept up to date by anything that changes a student's name.
- **Guardians and consent (`guardians`, `consent` modules, M5):** ask "may adult U act for child S" only through `guardians.GuardianAccess` (ACTIVE link, not custody-restricted, flag on; read per request) and consent only through `consent.ConsentService` (most restrictive wins; for media treat UNKNOWN as no: `mediaPublicationAllowed`). Guardians may *view* their child's classes (a `ClassAccessRule`) but never rosters or other children: roster and classmate endpoints use `ClassAccess.canViewRoster`/`rosterVisibleClasses`, never `canView`. Invitation tokens and parent codes are never stored, logged or audited (hashes only); restriction and decision notes never reach audit rows or events; `consent_records` is append-only.
- **Attendance and sync (`attendance`, `sync` modules):** rolls are written only by `RollService` (the online `PUT .../classes/{c}/attendance` and the `ATTENDANCE_MARK` sync operation share it): validate everything (access through `ClassAccess`, the school-local date, slot, lock window, class membership on that date) **before** writing or publishing anything; a mark that differs from a stored record is applied only with that record's `expectedVersion` (or the roll's current `baseVersion`, or the same device's own earlier edit), otherwise it is a CONFLICT result and nothing is overwritten; device time (`recorded_at`) never decides. Attendance dates are school-local `date`s computed with `SchoolTime` (campus zone, else school zone), never from the server's zone. Absence-report `reason_code` and `note` are health data: only the reporter, the student's LEAD/CO/SUBJECT teachers and `school.attendance.manage` read them; never in events, notifications, logs or audit metadata. The offline endpoint `POST /api/v1/sync` is generic: a module adds an operation type by registering a `sync.SyncHandler` bean (authorize exactly like the online endpoint, validate first, throw `ApiException` to REJECT, return `SyncOutcome.conflict` for CONFLICT, `SyncOutcome.duplicate` when the online path already applied the same client operation id, e.g. `AwardService` with `clientOpId`); each operation runs in its own transaction and is stored in `sync_operations` (payload and state purged after 30 days), so never call the sync service from a handler. `ATTENDANCE_MARKED` goes only to the statuses in `attendance.notify_guardians.statuses`; the streak badge is `AttendanceStreaks` through `PointsApi`. **QR check-in (M7e, `attendance.application`):** a scan is evidence, not authority, and has **one write path**: `RollService.markFromCheckin` (students; the staff twin is `StaffAttendanceService.recordFromCheckin`) applies the roll's own rules (school-local date, the lock window with no override, class membership on the date, PRESENT or LATE only, never overwrites: REJECTED_DUPLICATE or REJECTED_CONFLICT) and appends the append-only `attendance_checkins` ledger in the same transaction; never write a mark from a scan any other way. **Credentials (the static QR of a card) are not login codes (D6):** 128 random bits, only `HMAC(pepper key, token)` stored (`AttendanceKeys`, keys `school.attendance.secrets.*`, a map with an active id: old keys keep verifying and a credential found under one is re-hashed on its first scan), one live per person, revoked with a reason, returned once at issue with `Cache-Control: no-store` and **never `@Idempotent`**. Rotating codes are `HMAC(qr key, session | window)` (current and previous window only, nothing stored per session). **Tokens, codes, hashes and keys are never logged, audited, put in an event, an error, a notification, a `toString` or the sync ledger** (`SyncHandler.storedPayload` strips the token; `CheckinNoSecretLeakTest` is the canary; give every request or answer record that holds one a redacting `toString`). A refused scan is a **logged answer (409 with a `CheckinResult` body), not a thrown error** (throwing rolls the ledger row back; a sync handler that must keep its writes returns `SyncOutcome.rejected`); an unknown, malformed, expired or other-school token is always the same `REJECTED_INVALID` and only a revoked card of the scanner's own school says so. **No location is requested, accepted or stored anywhere in attendance (D38)**: never add a latitude, longitude, address or network column or field (tested). Check-in endpoints also need the school ACTIVE and the method on (`attendance.methods.enabled`); manual marking is always available. A new check-in endpoint needs its cases in `AuthorizationMatrixTest`, a rate limit and the abuse-case tests of M7e. **Per-period rolls (M7d):** one roll per class, date and slot; a subject only on P1..P8, only one of the class's active `class_subjects`, fixed when the roll is created (`attendance.subject_mismatch`); `groupId` (a saved `student_groups` group) only narrows the roster of a request and is never stored. **Staff attendance (M7d, `staff_attendance_*`):** read only through `StaffAttendanceService` (`school.staff_attendance.read/manage`, setting `attendance.staff.enabled`, feature `attendance`) or by the staff member for their own records: **a teacher never reads a colleague's record** (a single record the caller may not read is 404, a list 403), no query for classes, points, badges, students or guardians may touch these tables, no leave, pay or HR data (D14); marking only creates, a change is an append-only correction with a reason, and no reason, note or name goes into audit metadata, events or logs. Reports and CSV exports of attendance are audited and rate limited like `attendance/report.csv`.
- **Points and badges (`engagement` module):** `point_transactions` is append-only (an undo is a REVERSAL row; never update or delete); write it only through `AwardService` (or `PointsApi.awardAsSystem` from other modules), which checks access through `ClassAccess`/`GuardianAccess`, is idempotent per (awarder, `client_op_id`) with an advisory lock plus the unique index, and publishes `PointTransactionRecorded`. Guardian awards are HOME only (D2) and HOME is excluded from every class or school aggregate, ranking, badge rule and report: any new query over the ledger for a class or the school must filter `context in ('CLASS','SCHOOL')`. `point_balances` is a projection recomputed from the ledger by idempotent listeners (never add deltas); the note (`reason`) is child data: never in logs, audit metadata or events. Read endpoints split school and home sections; the leaderboard stays off unless the school enables it. A new badge rule type goes in `BadgeService.validateCriteria` and `BadgeEngine`; badge grants stay unique per student and badge. Categories and badges are deactivated, never deleted; schools get copies of the platform templates (`R__70`, `EngagementSeeding`).
- **Feed (`feed` module, M8):** posts and stories of a class or the school; contributions of guardians and students; comments, reactions, "seen by" counts; translation. Rules that every change must keep: (1) **visibility** comes from one SQL definition (`FeedVisibility`: `ClassAccess.visibleClasses`, which holds the guardian rule, for class content; school membership or `school.feed.manage` for school content; PUBLISHED only; stories also `expires_at > now`) used by lists, single reads and the media policies, so they cannot disagree; **never read a post or story by id without it** (`PostViews.requireReadable`). (2) **Consent gate (R-09)**: whatever makes media visible (publish, schedule, scheduler, approval, republish, edit of tags or photos, story) calls `ConsentWithholding.check`; untagged media needs the author's confirmation (kept in `media_confirmed_*`, audited); every read re-evaluates `ConsentService` for the tagged students and withholds the photos (`mediaWithheld`) from everyone but the author and moderators: nothing is cached, so a withdrawal applies at once. (3) **Media** (purposes `POST`, `STORY`, contexts `CLASS`/`SCHOOL`, images only) is read only through its post or story (`PostMediaPolicy`, `StoryMediaPolicy`); payloads carry media ids and variant names, never URLs. (4) **People in payloads** go through `FeedViewer`: tagged students (BASIC data) only to those who may know them, guardian and student authors by role label unless the viewer is staff of the class, themself, or (students) a classmate or the student's guardian; "seen by" is a count. (5) **Moderators** are the class's LEAD teacher, class managers and `school.feed.manage`; authors edit only their own posts; a contribution is editable only while pending. (6) Translation sends only masked text of published content through `TranslationProvider`; off by default. (7) New feed notification types need rows in `R__50` and keys in both bundles; listeners use `alreadyNotified`; push text never contains post text, moderation reasons or a child's name. (8) Request records use `Boolean`, not `boolean`, for optional flags (the JSON mapper rejects a missing primitive).
- **Communications (`communications` module):** announcements are plain text only (no markup is interpreted anywhere; `BodyText` cleans control and bidirectional characters) and carry an explicit audience (SCHOOL, CAMPUS, GRADE_LEVEL, CLASS, USER) with roles GUARDIAN, STUDENT (setting, default off) and STAFF (managers). Who may address what is `AnnouncementAccess.authorize` (`school.announcements.manage`; LEAD and CO teachers and class managers only their own classes; URGENT and SAFETY need `school.announcements.urgent`). Recipients are a snapshot written at publish by ONE SQL statement (`AudienceResolver`: guardians through their children, one per adult, never restricted, pending or revoked links); reading is the same rule from the person's side (`AnnouncementAccess.readable`, late joiners can open it, a lost link loses access); if you change one, change the other (`AnnouncementAudienceTest` compares them). Delivery is chunked (500, `FOR UPDATE SKIP LOCKED`, resumable, idempotent) through `NotificationService` with the title and school name only, never the body or a child's name; the scheduled-publish and resume jobs return `Integer`. Delivered (`notified_at` and the channel statuses), read and acknowledged (`announcement_acknowledgements`) are separate records. Audit rows carry ids, type, audience kinds and counts, never text. Email and SMS are optional channels: SMS is off by default, only for the types in `announcements.sms.types`, capped per announcement and school day, through `SmsAdapter` beans chosen by the number's country (checklist: `docs/ops/sms-provider-adapter.md`); opt-outs always apply. Urgent and safety announcements use the notification type flags `urgent_overrides_preferences` and (for the others) `defer_in_quiet_hours`: a new announcement-like type sets them in `R__50_notification_types.sql`.
- **Messaging (`messaging` module):** the rule book is `docs/Messaging_Rules.md` (child safety: when a rule is silent, choose the most restrictive and document it; every rule has named tests). Every read and write goes through `MessagingPolicy` and the live SQL of `infrastructure.Eligibility`: a membership row never grants access, the account, school, class, guardian link (ACTIVE, not custody-restricted, `can_message_staff`) and `messaging.*` settings are checked on every request, and refusals the refused person meets are the generic `messaging.not_allowed` (unusable conversation = 404). Never call a `@Transactional` policy method that throws and catch it (it marks the outer transaction rollback-only): use the non-throwing `postRefusal`, `tryModeration`, `findGroupBasis`. Adult-student DIRECT conversations are safeguarded (`Safeguarding`: guardians as read-only OBSERVERs or `admin_visible`; reviewers read only through the audited, reason-bound review endpoint and are never members); a conversation with students needs two or more students. People are identified by member id, never user id; guardians only as role labels; no date of birth, gender, username, phone or e-mail ever. Message text lives in `messages`/`message_edits` only: never in audit metadata, events, notifications, pushes, realtime payloads (the doorbell carries ids) or logs (request records override `toString`; `NoTextLeakTest`). Order and watermarks use `messages.seq`, not the UUID. New message features need entries in `docs/Messaging_Rules.md`, a case in `MessagingPolicyMatrixTest` where they change who may do what, and `AuthorizationMatrixTest`.
- **Portfolios (`portfolio` module, M12a):** the rule book is `docs/Portfolio_Rules.md` (children's own work and photos: when a rule is silent, choose the most restrictive and write it down with its test). "May this user see this item" is one SQL predicate, `PortfolioAudience.viewable` (single read, every list and gallery, and `PortfolioMediaPolicy` use it, so they cannot disagree): a non-creator sees an item only when it is APPROVED, within its *effective* visibility (the lower of the item's `visibility` and the school cap `portfolio.max_visibility`, default GUARDIANS; the stored visibility is never rewritten); reviewers (class LEAD/CO_TEACHER, a SUBJECT_TEACHER with the item's subject, class managers via `ClassAccess.manageableClasses`, holders of `school.portfolios.review`) see every status but DRAFT. Files beyond the student's own guardians (CLASS/SCHOOL, or `shows_other_children`) need MEDIA_PUBLICATION consent for the student and every tagged child, or the creator's confirmation: the gate runs at approval/unarchive (`PortfolioConsent.check`) and the same test runs **live on every read** (`withheld`: `media: []`, `mediaWithheld`, signed URL 404); never cache it. Status moves live only in `PortfolioWorkflow`; every transition appends to the append-only `portfolio_approvals` (DB trigger). Portfolio text (titles, reflections, notes, comments, reasons) is plain text via `PortfolioText` and never goes to logs, events, audit metadata or notifications (`PortfolioNoTextLeakTest`); notifications use generic text. Media purpose PORTFOLIO takes images and PDFs only (audio/video are deferred, not weakened); the media module's `DELETE /media/{id}` now asks the purpose policy (`canManage`) instead of always letting the uploader delete. Sharing to the class story is deferred (422 `portfolio.share_unsupported`). Portfolios are entitled from `SCHOOL_BASIC`: tests build schools with `PortfolioTestSupport.basicSchool`.
- **Calendar (`calendar` module):** the calendar API is a **union** (R-17): `CalendarService` merges every `CalendarSource` bean (`EVENT`, `PERSONAL_EVENT`, `HOLIDAY`, `ACADEMIC_PERIOD`; later assignments and the published timetable are beans in their own modules (live sessions and tutoring sessions are removed, D33/D32), using only the top-level `calendar` package) and each source filters by the caller's access itself, in SQL (`CalendarQuery` carries the schools already checked, the optional child filter and the cap). Native events: visibility and "may change" live in `CalendarAccess` only (`visible` is one SQL predicate shared by the single event and the union; parent meetings are INVITEES-scoped and re-checked against `GuardianAccess`' rules at every read: custody-restricted, revoked and academics-less guardians never see them, administrators neither). All-day events are dates in the event's zone (`start_date`/`end_date` inclusive, instants stored as start of the first day and start of the day after the last); recurrence is the RRULE subset in `Recurrence` (expanded per window with caps, wall-clock in the event's zone; exceptions are `event_overrides` keyed by the occurrence's UTC instant; no EXDATE text). A new source or notification must keep titles and text of parent meetings out of push, audit and logs (they may name a child). Reminders: `CalendarMaintenance` (ShedLock, returns `Integer`), idempotent through `event_reminders`. Text blocks in SQL: a leading space in a text block's first line is stripped, so add a separator explicitly when concatenating.
- **Moderation and safeguarding (`moderation`, `safeguarding` modules, spec `docs/Safeguarding_Rules.md`):** other modules depend on neither, they implement the SPIs of `moderation` (`ReportTarget`: may this reporter see the target; `ModerationTarget`: hold, hide, restore and read for review, never destroying the original; `SchoolSuspension`) and call `ReportIntake.ingest` from an idempotent listener of their own event (the listener lives in the owning module). A new reportable target is one more bean; add its tests. **Text of a report, a decision reason, a narrative or a note exists only in its own table (incident text only as an AES-GCM envelope from `IncidentCipher`)**: never in events, logs, audit rows, notifications or list endpoints (`safeguarding.NoTextLeakTest` is the canary; give request records with text a redacting `toString`). Incident endpoints answer **404 as if nothing existed** to everybody but leads (`IncidentAccess`); reporter identity is for leads and platform moderators only; nobody is notified automatically about an incident. Notification texts of this area are generic (no content, names, outcome or case id). Hold, hide and delete of reported content go through the owner's `moderation_case_id`/`moderation_hidden_at`. Settings changes that a rule forbids are refused by a `tenancy.SettingChangeGuard` bean. Keys: `school.safeguarding.encryption.*` (dev key only in `application-local.yaml`; `DeploymentConfigValidator` refuses deployed profiles without a valid key). A matrix of every endpoint is `AuthorizationMatrixTest.everyModerationAndSafeguardingEndpointAllowsExactlyTheExpectedPersonas`.
- **Tests:** annotate integration tests with `@IntegrationTest` (shared context, Postgres 18 via Testcontainers). Keep its properties identical across classes so the context is reused (the server runs on a random port, so real WebSocket clients can connect). Call endpoints as real users from `support.Personas` (`persona.bearer()`; since M3a it includes school members: `TEACHER_LEAD_A`, `TEACHER_SUBJECT_A`, `TEACHER_OTHER_A`, `STUDENT_A1`, `STUDENT_A2`, `STUDENT_FORMER_A`, `STUDENT_B1` and the fixture classes in `Fixture`; tests that need to change settings or rosters create their own school with `personas.newSchool(...)`), add new endpoints to `AuthorizationMatrixTest`, and reset `MutableClock` after moving time.

## Product rules that apply everywhere

- **Authorization is server-side only.** Never filter sensitive data on the client (spec §100). Every endpoint gets allow/deny tests per role, including another school's admin.
- **Tenant isolation:** school-owned rows carry `school_id`, with composite FKs to the parent (Database_Design §1).
- **No hard-coded UI strings.** Add keys to `packages/i18n/messages/en.json` *and* `am.json`; the catalog test enforces identical keys and placeholders. Amharic text needs native-speaker review before release.
- **No country literals in code (D42):** country, time zone, calendars, languages, currency, calling code and phone rules, policy and safety text, and payment methods come from the database through `tenancy.CountryResolver` (school, then user home country, then organization, then the platform default country `platform.default_country`, which must be an ENABLED country; there is no literal fallback). Languages the backend has messages for come only from `common.i18n.SupportedLocales`. Clients read `GET /meta`, `GET /me` and the school summary, never constants. `NoCountryHardcodingTest` (backend) fails the build on `"ET"`, `"Africa/Addis_Ababa"`, `"ETB"`, `"+251"` and literal language lists with `"am"` and the web, mobile and packages have the same guard in `@school/config/eslint/no-country-hardcoding` (ESLint `no-restricted-syntax` on the AST, so comments are never matched): it fails `npm run lint` (CI `js`) on the literals `'ET'`, `'ETB'`, `Africa/Addis_Ababa`, `+251`, on literal `['en', 'am']` lists and on `=== 'am'` branches in `apps/web`, `apps/mobile` and every `packages/*`, except tests, `**/fixtures.*`/`**/fixtures/**` and generated code (`packages/calendar` and `packages/i18n`, the conversion algorithm and the list of UI catalogs, switch it off in their own `eslint.config.mjs`); the guard has its own test (`packages/config/eslint/no-country-hardcoding.test.mjs`). What stays code: calendar algorithms and the `DateSystem` enum, message bundle files, and provider adapters.
- **Dates:** store instants as `timestamptz` (UTC) and dates as Gregorian `date`. Ethiopian calendar is display-only, via `@school/calendar`, and always with an explicit timezone.
- **Validation messages** are i18n keys (`validation.*`), never English sentences.
- **Children's data:** media of students needs media-publication consent; minimise data sent to third parties; audit sensitive reads (spec §131).
- ClassDojo is a UX benchmark only. Don't copy its brand, characters, illustrations or copy.

## Git

- `main` is protected: every change goes through a PR, and the `js`, `backend` and `migrations` checks must pass. Branch from `main` and open a PR.
- Dependencies: Expo-managed packages (React, React Native, `expo-*`, `react-native-*`) only move together via `npx expo install --fix` during an Expo SDK upgrade, and Dependabot ignores them. Majors of Next, ESLint and TypeScript are upgraded deliberately, not by Dependabot.
- Don't commit secrets or `.env` files. Dev-only credentials live in `infra/` and `application-local.yaml` and are documented as such.
