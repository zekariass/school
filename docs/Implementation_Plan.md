## A3. How to implement a milestone, step by step

1. **Pick the milestone and check its status** in part B. Implement only what is marked ⬜, 🟡 or 🔧. If it depends on a milestone that is not done, stop and say so.
2. **Read:** `CLAUDE.md`; the milestone section; every DB section, spec section, decision and rule book it cites; the as-built notes of the milestones it builds on (they describe the real APIs, which sometimes differ from the original design).
3. **Branch** from an up-to-date `main`: `m<number>/<short-name>` for features (e.g. `m7d/staff-attendance`), `docs/<topic>` for documentation, `fix/<topic>` for fixes. Work in your own git worktree when several agents work at once.
4. **Ports and databases when several agents run in parallel:** Postgres (:5442) and Redis (:6390) are shared; give each agent its own database `school_<tag>`, an API port from 8180 upwards, a web port from 3100 upwards and a Metro port from 8081 upwards. Check which are taken before you start.
5. **Backend first** (when the milestone has one):
   - **Migration.** Use the **next free major version after the highest existing `V` file** (today the highest is `V13_02`; the next new milestone uses `V14_01`, and so on in delivery order). **Do not name a migration after the milestone number**: Flyway refuses a version lower than one already applied, and milestones are not delivered in numeric order. Seeds (features, settings, permissions, roles, notification types, policies) go into the matching `R__` file. School-owned tables carry `school_id` with composite foreign keys (DB §1).
   - **Module code.** Follow `CLAUDE.md` exactly: `ApiException` with a stable snake_case code plus `error.<code>` in both `messages.properties` and `messages_am.properties`; `@PreAuthorize("@authz.school(...)")` or `AccessControl`; actors from `CurrentUser`; `Clock` and `Ids.newId()`; keyset pagination (`CursorPage`); events published inside the transaction and consumed by idempotent `@ApplicationModuleListener`s; jobs with `@Scheduled` plus `@SchedulerLock("<module>.<job>")` returning `void` or an object, never a primitive; `AuditLog.record(...)` for every mutation (no secrets, mask phones and e-mails); `@Idempotent` on create endpoints.
   - **Cross-module access** only through another module's top-level package (ports, events, SPIs). Never reach into another module's `application` or `infrastructure`.
   - **Tests** (`@IntegrationTest`, Testcontainers, real users from `support.Personas`): allow/deny for **every** role the milestone lists, including another school's administrator; add every new endpoint to `AuthorizationMatrixTest`; abuse cases where the milestone lists them; `MutableClock` reset after moving time.
6. **API contract:** run `npm run openapi:export -w school-backend`, then `npm run codegen`, and commit both `openapi.json` and the generated client. CI fails on drift.
7. **Web and mobile** from the generated client. Follow the per-feature privacy rules in `CLAUDE.md` (what may be stored, logged or put in URLs). Every string is an i18n key in `en.json` **and** `am.json`; mobile `mobile.*` messages are **plural-free** (Hermes has no `Intl.PluralRules`).
8. **Run the checks** and make them pass: `npm run lint typecheck test` (or the filtered equivalents) and, for the backend, the full `npm run test -w school-backend` (or at least the module's tests plus `ModularityTest`, `MessagesTest`, `NotificationTypesSeedTest`, `RolesAndPermissionsSeedTest`, `OpenApiSpecTest`, `AuthorizationMatrixTest`). Web changes that touch layouts must also pass `npm run build -w school-web` (`cacheComponents` violations only show there).
9. **Update the documents in the same PR:**
   - In this plan: add an **"As built"** note under the milestone (template in A5), change its status mark in part B and on its heading, and add new follow-ups to part C.
   - In `Database_Design.md`: an "As built" note with every deviation from the DDL.
   - In `CLAUDE.md`: a short conventions paragraph if the milestone adds a module or a cross-cutting rule (look at the existing ones for messaging, feed or attendance).
   - In `Spec_Review.md`: any new decision the owner made.
10. **Pull request:** one PR per milestone slice (backend, web and mobile may be separate PRs, as in M7a/b/c). Required CI checks: `js`, `backend`, `migrations`. Describe what was built, what was not, the decisions you made, and how you verified it. **Never merge your own PR without the owner's approval**, and never push to `main`.

## A4. Definition of done (every slice)

1. The Flyway migration matches `Database_Design.md` (or the DB document has an as-built note) and applies to a fresh database and on top of the previous release.
2. Authorization is enforced on the server (`authorization` module, `AccessControl`, `ClassAccess`, `GuardianAccess`). The client never filters sensitive data.
3. Each endpoint has an **allow/deny test** for every relevant role: student, teacher (lead, co, subject, assistant), guardian, custody-restricted guardian, unrelated guardian, tutor, school administrator, campus administrator, **administrator of another school**, and the special roles the milestone names (safeguarding lead, platform moderator, bursar, finance manager…).
4. The OpenAPI snapshot and the generated client are updated (CI fails on drift).
5. Web and mobile screens exist in English and Amharic, with loading, empty, error and offline states, and meet accessibility basics (labels, contrast, dynamic type, `prefers-reduced-motion`).
6. Mutations write `audit_logs` (ids, codes and counts only: never secrets, children's free text or health data). Domain events go through the Spring Modulith outbox (`event_publication`). Notifications use registered `notification_types` with generic texts.
7. Analytics events for the §133 release gates are emitted (once M14 has the analytics pipeline).
8. The module README (`apps/backend/src/main/java/com/nemaz/school/<module>/README.md` or the `package-info.java`) describes its rules, settings keys and permissions.
9. The documents of A3 step 9 are updated.

## A7. Product rules that apply everywhere (summary of `CLAUDE.md`)

- Authorization is server-side only; tenant isolation through `school_id` and composite foreign keys; a school-scoped endpoint answers 404 to those who cannot see the school or object and 403 to members without the permission.
- Children's data: no names, notes, health data or free text in URLs, logs, analytics, audit metadata, events or push texts; ids only in paths; media of students needs media-publication consent; signed media links are never persisted.
- No hard-coded UI text; validation messages are `validation.*` keys; Amharic texts need native-speaker review before release.
- Instants are `timestamptz` (UTC); dates are Gregorian `date`; the Ethiopian calendar is display-only through `@school/calendar`; every date calculation uses an explicit time zone (the school's for school data).
- ClassDojo is a UX benchmark only: never copy its brand, characters, illustrations or copy.

### UI benchmark rule (ClassDojo)
ClassDojo is a reference for **patterns and quality** only:
- avatar-grid class view and one-tap points
- story feeds
- parent home focused on the child
- translate-in-place messaging
- the teacher toolkit
- a friendly, rounded, high-contrast visual style

We don't copy its trademarks, monster characters, illustrations, sounds or copy text. The product gets **its own** avatar system and brand (M0.5).

Polling (`pollDelayMs`) runs only while VALIDATING or COMMITTING (1 s, slower for long runs) and stops on a 4xx.
- **Upload:** `IMPORT_FILE` through `lib/media/upload.ts` with the school as context. Browsers disagree on the CSV type (empty, `text/plain`, the Excel type), so `lib/school/import/files.ts` decides the type from the name (`.csv` to text/csv, `.xlsx` to the workbook type; `.xls` and `.xlsm` are refused before upload) and re-wraps the `File`. The create call carries an `Idempotency-Key` that is renewed per file and type.
- **Columns step:** encoding, separator and sheet dropdowns re-read the file through the new preview parameters (below); one select per field with a sample value, required and "one of" markers, the missing list; date system; saved mappings (apply, delete, save under a name; the API's auto-applied profile is shown). "Check the file" saves the mapping and starts the dry run in one go.
- **Review step:** counts, filter chips (all, problems, possible duplicates, ready, left out), keyset-paged rows with localized problem messages, "show the row as in your file", possible duplicates with the candidates and LINK / CREATE_NEW / SKIP, the error report (fetched through the BFF, saved as a Blob, never cached), "leave out the invalid rows" and the commit confirmation naming the counts that will be created, updated and left out. A refused commit reloads the job (out of date: back to the columns or to a new check).
- **Privacy:** rows, previews and candidate lists exist only in TanStack memory (`gcTime` 30 s); nothing goes to URLs, storage or logs. The error report and templates are downloaded with `cache: "no-store"`.
- **Backend changes (small, made for this UI):** `GET /imports/{id}/preview` accepts `encoding`, `delimiter` and `sheet` (any of them, empty meaning detect) and returns the preview of the file read that way with a fresh suggested mapping, saving nothing (without it the reading override could not be tried before a complete valid mapping exists); `CommitResult.guardianContacts` counts the parent contacts the job staged ("N parent contacts saved for invitation"; only in the single-job read). OpenAPI and generated types regenerated; `StudentImportApiTest` covers both.
- **Not done / follow-ups:** no component tests (the web test setup is node-only: the pure logic is tested); the Amharic text needs a native speaker; a pre-commit count of staged parent contacts; XLSX error report; guardian UI (M5 web); a "with warnings" row filter (warnings are shown on the rows, the filter is server side by status only).

The lock is derived (status stays SUBMITTED). 404 for callers who cannot see the class, 403 for members who may not take it (students and guardians of the class included).
- **Versions and conflicts:** each record has a `version` (0 on creation, +1 per change); the roll has a `sessionVersion`. A mark identical to the stored record is UNCHANGED (two teachers who agree do not clash). A mark that differs is written only when the writer saw that record: its `expectedVersion` equals the stored one, or the request's `baseVersion` equals the current `sessionVersion` (nobody changed the roll since), or it is the same sync device's own earlier edit (same user and device, device time not before the stored one: a queue edits one record twice). Otherwise it is a CONFLICT that carries the stored record and the submitted mark, and nothing is overwritten; the other marks of the same request are still written. Online: 200 when no mark conflicted, 409 with the same body when some did. **The first write in the server's state stays; the device time (`recorded_at`) is kept and clamped but never decides** (this replaces the "latest recorded_at wins" rule of DB §4.6: a later device clock cannot overwrite a colleague's mark silently).
- **Sync protocol** (`POST /api/v1/sync`, module `sync`): the body is `{operations: [...]}` (at most 100 operations and 1 MiB; 413 `sync.too_many_operations` / `sync.payload_too_large`; 429 `sync.rate_limited` at 120 requests a minute per user; a malformed operation, such as a missing id, is a 400 for the whole request). Each operation has `deviceId` (a UUID the app makes once at install; **not** a `push_devices` id, so a device syncs without push), `clientOperationId` (a UUID per queued operation), `operationType`, `entityType`, optional `baseVersion`, `payload` (at most 64 KiB) and `clientCreatedAt`. The answer is always 200 with `results`, one per operation in the same order: `APPLIED` (with `entityId`, `version`, `state`), `DUPLICATE` (the operation was seen before: the first outcome, with `originalStatus` and the stored `state`; replaying a whole batch is safe, also in parallel), `CONFLICT` (`state` says per student what is stored and what was sent; nothing was overwritten), `REJECTED` (`problem.code/status/detail`, stored: it will never succeed as sent, so do not resend; make a new operation). Operations run in order, each in its own transaction, and a failing one never blocks the next. Authorization is the online endpoint's, at sync time: a removed teacher gets REJECTED `class.not_found`, an archived class `class.archived`, a student who had left `attendance.student_not_in_class` / `points.student_not_in_class`, a locked roll `attendance.session_locked` (or `attendance.override_reason_required` for the lead). Transient failures (429, 5xx, unexpected) are not stored: the result says `retryable: true` and the same operation may be sent again. Time: `clientCreatedAt` is stored as sent; the effective time (`recordedAt`) is the same unless it is more than 5 minutes ahead of the server (then the receipt time, `timeAdjusted: true`); an operation older than 30 days is REJECTED `sync.operation_too_old`. ### M7e Attendance QR check-in (≈ 2 weeks, after M7d; Sonnet high, the lead reviews the credential and check-in endpoints)

**Status:** ⬜ To do

**Depends on:** M7d (staff records), M7 (`RollService`, sync outbox). **Read first:** DB §4.34, spec §134.5, D17, D19, D38, the M7a and M7b as-built notes.

Tables: DB §4.34. Spec §134.5. Decisions D17, D19, D38. **Scope: manual marking (already built) and QR only.** NFC, RFID, GPS, kiosks and gate readers are not part of the product; no location is requested or stored anywhere in attendance.

1. **Credential service.** `attendance_credentials`: a 128-bit random token printed as a QR on a **credential sheet** (printed like the login-code sheets) until M35 prints it on the ID card, stored as an HMAC with a server pepper kept in the secrets store (rotation procedure documented), revocable with a reason, one live credential per student or staff member. A credential carries no personal data and is never the login code of D6. A scan answers the scanning teacher with **first name and avatar only**.
2. **One write path.** `RollService.markFromCheckin(...)` creates PRESENT or LATE through the same validation as the online roll and `/sync` (school-local date, lock window, class membership on the date, conflict rule). A check-in never writes ABSENT and never overwrites a different stored mark (`REJECTED_CONFLICT`). Every attempt, accepted or not, is stored in `attendance_checkins` (append-only).
3. **Rotating QR (the student scans the teacher's code).** `attendance_qr_sessions`: the code is `HMAC(server key, qr_session | floor(t / rotation_s))`, so no per-session secret is stored; the server accepts the current and previous window; the caller is an authenticated student session; one accepted check-in per student per session; per-student and per-class rate limits; the teacher's live list, with the ability to remove an entry. The teacher screen shows a countdown and works for the display without a connection.
4. **Static QR (the teacher scans the student's card).** Teacher phone scan with `expo-camera`, queued through the sync outbox with a `client_op_id` so a scan taken offline applies once. A scan of a revoked or expired credential is refused and logged with the scanner; two scanners reading one credential within a minute raise an alert (`SUSPECTED_COPY`).
5. **Staff check-in.** A manager opens a staff QR session for a campus and day and shows the rotating code; staff scan it. A manager can also scan a staff member's static card. Results go to `staff_attendance_records` under the M7d rules.
6. **Settings and admin.** `attendance.methods.enabled` (`MANUAL`, `QR_ROTATING`, `QR_STATIC`), `attendance.qr.rotation_seconds`, `attendance.staff.late_after_minutes`; credential issue, revoke and reissue on the student page; a plain-language notice to schools of the two known limits (a rotating code can be photographed and shared; a static card can be copied).
7. **Tests (abuse cases, mandatory):** replayed and expired codes, previous-window acceptance, a student scanning for a class they are not in, a code from another school, a duplicate scan, revoked and expired credentials, a credential scanned for another school's student, conflict with a teacher's mark, the lock window, a scan after the roll's window, rate limits, the offline replay (DUPLICATE on the second send), and a test that no check-in endpoint accepts or stores a location. Allow/deny matrix additions for every endpoint.

**Exit:** a pilot class uses the rotating QR for a week with no roll conflicts; a student card scanned by a teacher marks the student present; a lost card is revoked and its next scan is refused and visible.

### M11 Calendar & events (≈ 1–2 weeks)

**Status:** ✅ Done (#44, #47, #48) · 🔧 part C: U-05, U-22

**As built: M11a calendar and events backend (26 Nov 2026, backend only).** Steps 1, 2 and 4 as an API contract (`openapi.json`); the month, week and agenda views with the Ethiopian toggle (step 3) are M11b (web) and M11c (mobile). New module `calendar` (`api`, `application`; public: the SPI `CalendarSource` with `CalendarQuery` and `CalendarItem`); migration `V11_01__calendar.sql`; settings, permission and notification types are repeatable seeds; deviations in DB §4.14. Decisions:
- **Scopes and rights.** SCHOOL, CAMPUS and GRADE_LEVEL events need the new permission `school.calendar.manage` (platform, country, organization and school administrators). CLASS events: that permission, `class.manage` over the class, or an ACTIVE LEAD/CO_TEACHER (setting `calendar.teachers_can_create_class_events`, default on). PARENT_MEETING: an ACTIVE LEAD, CO_TEACHER or SUBJECT_TEACHER of a class the student is ACTIVE in (not assistants, not administrators). PERSONAL: any signed-in user. Types follow the scope (SCHOOL_EVENT/EXAM/OTHER for school, campus and grade; CLASS_EVENT/EXAM/OTHER for a class; OTHER for personal). Text is plain text, cleaned like M10a (`common.text.PlainText`).
- **Visibility** is one SQL predicate (`CalendarAccess.visible`) used by the single event and the union alike: school-wide events for ACTIVE staff, ACTIVE students and guardians (ACTIVE link, not restricted) of an ACTIVE student, plus `school.read` holders; campus events for the people of that campus (staff without a campus see every campus; students by their campus or class campus; their guardians); grade events through the ACTIVE classes of the grade; class events through `ClassAccess.visibleClasses` (teachers of any role, students, managers, guardians with academics access; former members nothing); PERSONAL only the owner; **parent meetings only the organiser and the invited guardians whose link still is ACTIVE, unrestricted and allows academics (re-checked on every read; a guardian linked after the invitation is not invited), administrators included.** A guardian's `studentId` filter narrows everything to that child.
- **Recurrence** is a small tested implementation of the RRULE subset (no library: the Java ones predate Java 25 or pull in a calendar stack): DAILY/WEEKLY(BYDAY)/MONTHLY(BYMONTHDAY), INTERVAL up to 99, UNTIL (date or UTC instant, at most 10 years after the start) or COUNT up to 1000; the first occurrence is always the event's own start (a rule that does not match it is refused); wall-clock times survive daylight-saving changes in the event's zone; monthly on the 31st skips short months. Rules outside the subset are `event.recurrence_unsupported`. Expansion is for the requested window only (window at most 366 days; at most 500 occurrences per series and 2000 items per source per request; `truncated` says so); an occurrence is named by the UTC instant it has in the series (`20261207T060000Z`), cancelled (EXDATE) or changed (moved by at most 7 days, same kind) through `event_overrides`; changing a series' schedule clears its exceptions. RSVP is not available on repeating events.
- **Parent meetings and RSVP.** Meetings carry `regarding_student_id`, are future-dated, timed and not repeating; the guardians resolved at creation get an invitation (`EVENT_INVITATION`) and a PENDING row; YES/NO/MAYBE until the start (same answer again: no change), RSVP reset on a reschedule, the organiser alone sees each guardian's answer; ordinary events with `rsvpEnabled` let everybody who sees them answer and show totals (never names) to managers. The audit entry of an answer holds the answer and the totals only; no audit entry holds a title, text or child id.
- **Notifications.** No push for a new ordinary event (setting `calendar.notify.new_events`, default off); cancellations and moves (time or place) of ordinary events notify the audience (guardians who allow notifications and staff, never the actor, never students; setting `calendar.notify.changes`, default on); parent meetings always notify their participants. A parent meeting's notifications never carry its title, description, place or the child (they say "parent meeting", the teacher's name and the time); ordinary events carry their title only. Quiet hours: the three new types defer their push to the end of the recipient's quiet hours.
- **Reminders.** `CalendarMaintenance.sendRemindersJob` (every minute, ShedLock `calendar.send-reminders`, returns `Integer`) sends `UPCOMING_EVENT` once per person per occurrence (memory: `event_reminders`), one day before events (`calendar.reminder.event_minutes`) and one hour before parent meetings (`calendar.reminder.parent_meeting_minutes`); 0 turns them off. Who: the owner of a personal event; the organiser and the still-valid guardians of a parent meeting; other events: those who answered YES or MAYBE, or everybody in the audience with `calendar.reminder.audience = EVERYONE` (those who said NO are never reminded).
- **The union** `GET /api/v1/calendar` asks every `CalendarSource` bean (`EVENT`, `PERSONAL_EVENT`, `HOLIDAY`, `ACADEMIC_PERIOD`; later `ASSIGNMENT`, `TIMETABLE` plug in as beans in their own modules) for the caller's window; each source filters by the caller's access in SQL. Holidays: the school's own and those of its country (and its area); academic years and periods: start and end dates as one-day all-day items. Items are ordered by (start, id) and keyset paged; the union leaves the caller's personal events out when a school or child is named unless `sources` asks for them.
- **Not built (open):** invitations for guardians linked after a meeting was created, a "remind me" per user, ICS export and feeds, free/busy and room booking, COURSE-scoped events (P3), multi-language event text (events are single-language plain text), event attachments.

### M31c Verify external payments with Veritas (≈ 3 weeks, needs M31b; **Opus**)

**Status:** ⬜ To do

**Depends on:** M31b; Veritas terms, privacy policy and plan (Spec_Review open item 2). **Read first:** DB §4.36, D37.

Tables: DB §4.36 (`verification_providers`, `school_receiving_accounts`, `external_payment_claims`). Decision D37. **Security-critical (money, third-party data).** This is the "pay through your bank or wallet, then verify" path.
0. **Terms and spike first (about 3 days).** Before any design is final: read Veritas's terms and privacy policy (Spec_Review open item 2), choose a plan, get a key, and **record each method's real answer** (CBE, Telebirr, Dashen, Abyssinia, CBE Birr, M-Pesa; successes, not-found, wrong suffix, and an HTTP 200 failure) as fixtures in a contract test, because the service documents no response fields. Confirm whether Telebirr lookups work from the hosting region. If the spike shows the service is unusable, the manual path and check.et remain.
1. **Verification port and Veritas adapter.** A `PaymentVerifier` port with a `VeritasVerifier` (https://veritas.et; hosted API, `x-api-key` header, key in the secrets store). The adapter chooses the **dedicated route from the method the guardian picked** (never auto-detection), **validates the reference format per method** before spending a credit (for example a 10-character Telebirr reference, a 16-character Dashen reference, a CBE `FT` reference), maps each method's answer into one internal `VerifiedTransfer` (amount, currency, paid time, receiver account, payer name, status) and treats **HTTP 200 with `success: false`** as a failure; **a missing or unexpected field is NEEDS_REVIEW**. Lookups run in a **background job** (the claim shows "checking") with a **65-second timeout**, one retry for network errors only (each lookup uses a credit), a **rate limiter below the plan's requests a minute**, and a circuit breaker. Raw responses are never logged or stored. A second adapter (check.et) can be added behind the same port.
2. **School receiving accounts:** `school_receiving_accounts` (method, account name, number encrypted at the application level, last four shown) managed by `school.fees.manage`; the claim check compares the provider's receiver account with these rows.
3. **Claims:** a guardian with `can_pay_fees` submits the method, the transaction reference, optionally a screenshot and the invoice. The reference is normalized and length- and charset-checked; **one live claim per transaction on the whole platform** (`ux_claim_reference_live`). The service is asked for the transaction; **only the reference and the second identifier the method needs (an account suffix, or the payer's phone for CBE Birr; stored encrypted and erased when the claim ends) leave the platform, never a child's name, a student id or the school** (contract test on the outgoing request).
4. **Acceptance rule.** A claim becomes VERIFIED (and produces a `VERIFIED_TRANSFER` manual payment, an allocation and a receipt) only if, from the provider's answer and never from what the guardian typed: the transaction exists and succeeded; the receiver matches an active receiving account of this school; the currency is the invoice's; the paid time is not in the future and not before the invoice was issued (minus a tolerance); the reference is unused; and the **verified amount** is used (less than the invoice: part-paid; more: a credit). Anything else, a provider error or a timeout goes to **NEEDS_REVIEW** for a finance user. The guardian sees "checking", "confirmed" or "we need a person to check".
5. **Abuse and cost controls:** 5 claims an hour per guardian and 20 a day per child; **each school's lookups are capped per month** (`fees.claims.monthly_cap`; past the cap a claim goes straight to a person) so the platform's single Veritas key and its monthly credits are not exhausted by one school; the provider's **masked payer name** is shown to the reviewer; a **daily in-app digest of auto-confirmed claims** (`FEE_CLAIMS_DIGEST`, a count and a link; no names or amounts) goes to the finance users; a payer who finds their reference "already used" can **dispute** it (`DISPUTED`); a school may require review for every claim (`fees.claims.auto_confirm`, default on). **Residual risk, accepted and documented:** the service proves that a transfer exists, not whose it is, so a guardian could claim someone else's transfer; the controls above make it visible and recoverable.
6. **Screens:** guardian "I paid elsewhere" flow (web and mobile), the finance review queue with the provider's answer, a claims log.
7. **Tests:** a reference used twice in parallel (one wins), a transfer to another school's account, a wrong currency, an amount below the invoice, a date before the invoice, a provider timeout, a malformed answer, an HTTP 200 failure and a missing field (all NEEDS_REVIEW), a reference in the wrong format (refused before any lookup), the monthly cap, the rate limiter never exceeding the plan, a claim for another family's child (refused), a claim against another school's invoice (refused), the outgoing request carries no student data, API keys never in logs or responses, rate limits, the circuit breaker opening and closing, and the manual fallback working with the provider down.
**Exit:** a guardian pays through a bank app, submits the reference, and the invoice is confirmed within about a minute with a receipt (longer if the service is slow); a doubtful claim lands in the review queue.

## Cross-cutting tracks (run throughout)

| Track | Practice |
|---|---|
| **Security** | Deny-by-default authorization. Tenant-isolation tests for every endpoint. Rate limits. Secrets in a vault. Dependency scanning. Yearly external pen test, plus one before each phase launch. |
| **Testing** | Unit tests for domain policies. Integration tests with Testcontainers. Authorization allow/deny matrix. Contract tests against the generated client. Playwright end-to-end for web. Maestro end-to-end for mobile. Offline and sync scenario tests. |
| **Performance** | p95 API < 300 ms for feed, inbox and roster. Mobile cold start < 3 s on a mid-range Android. Low-data budgets per screen. |
| **Localization** | Every string in catalogs. Native-speaker review for each language. Ethiopian calendar display. Country-labelled name and address fields (R-37). |
| **Accessibility** | WCAG 2.2 AA target on web. Platform accessibility APIs on mobile. |
| **Observability** | Traces across web/mobile → API → jobs. Dashboards for sync success, notification delivery, payment webhooks. |
| **Documentation** | Module READMEs. ADRs for major choices (auth, jobs, offline store, providers). Runbooks. A seed script for a demo school. |
| **School-operations security** | Abuse-case tests are part of each milestone's definition of done (M7e, M22, M27, M31a–c, M40–M42): replay, forgery, enumeration, two-person-rule bypass, cross-tenant and cross-user access. Public endpoints (`/verify/{token}`, payment webhooks) are rate-limited, constant-time, uniform on failure and side-effect free until verified. Secrets (HMAC peppers for credentials and verification tokens, webhook keys, the verification-service API key) live in the vault with a documented rotation. Financial and issued-document tables have no update or delete path. Exam answers, card tokens, receiving-account numbers and message text are never logged; no location is collected anywhere. A new endpoint is added to `AuthorizationMatrixTest` in the same change |
| **Compliance** | Consent coverage reporting. Data processing agreements with every processor. Country legal review before each new market (§131). |
